Java vs Rust vs C++ for a 100µs-tail FX market-making platform

1. Executive verdict

Do not approve a wholesale Java → Rust rewrite solely because Rust is perceived to be faster. Approve a measured, component-level benchmark and, if justified, adopt Rust or C++ only for the measured hot-path components that cannot meet the latency budget in disciplined Java.

A sub-100µs p99.99 end-to-end FX pricing and deal-acceptance target is a system-design and operating-environment problem, not a language-selection problem. Java, Rust, and C++ can all participate in platforms that hit 100µs tails. The difference is how much engineering discipline, ecosystem support, operational tuning, and specialist talent each requires.

Java
Best default when current stack is Java and target is ≥100µs p99.99.

Strongest finance ecosystem: Aeron, Agrona, SBE, Chronicle, Disruptor, JMH/JFR, mature FIX. Needs allocation-free hot paths and JVM discipline.

Rust
Best candidate for new native, memory-safe hot-path components.

No GC/JIT warm-up, strong compiler safety, C/C++-class runtime. Weaker finance-specific ecosystem and smaller hiring market.

C++
Best where the last microseconds and vendor/HFT integration dominate.

Deepest low-latency ecosystem and hardware-adjacent control. Highest memory-safety and key-person risk.

FPGA
Only for sub-µs / deterministic hardware-gate use cases.

Treat as a special investment case; talent and support constraints can dominate the business case.

2. Decision tree: language choice by latency goal

This tree assumes the target is end-to-end p99.99 latency unless otherwise stated. Component-level budgets can be tighter; for example, a 100µs end-to-end path may require individual hops in the 5–30µs range.

Decision principle: retain Java for broad business logic, state management, control plane, booking, exposure, monitoring, and most FIX workflows; introduce Rust/C++ only where the measured hot path requires native determinism or hardware-adjacent integration.

4. What “100µs at four 9s” really means

Java

Java should not be dismissed as “too slow” for FX market making. Its problem is not steady-state speed; it is tail predictability when ordinary Java allocation, blocking queues, locks, logging, and framework abstractions enter the hot path. Modern low-latency Java deliberately looks unlike enterprise Java: primitive arrays or direct buffers, Agrona collections, SBE codecs, single-writer event loops, JIT warm-up, explicit GC strategy, pinned threads, and no allocation after startup.

Where Java is compelling

  • Existing team and codebase are already Java.
  • Aeron/Agrona/SBE/Chronicle are strategic dependencies.
  • p99.99 target is around 100µs or above and the system can be made allocation-free.
  • FIX, state, audit, replay, controls, and operational tooling matter as much as raw speed.

Where Java becomes risky

  • Component budget approaches <50µs p99.99.
  • Hot path still allocates or hits generic queues/loggers/frameworks.
  • JVM warm-up, safepoints, deoptimization, or GC cannot be made irrelevant.
  • Networking requires kernel bypass/hardware-specific APIs with stronger native support.

Oracle describes ZGC as a scalable low-latency collector that performs expensive work concurrently and avoids stopping application threads for more than a millisecond, with heap-size-independent pauses.[S5] That is impressive for most systems, but a platform targeting 100µs p99.99 cannot rely on “sub-millisecond GC” in its critical path. The practical rule remains: no allocation in the pricing/distribution hot path after warm-up.

Rust

Rust’s credible case is not that it magically beats optimized Java in every benchmark. Its credible case is that it gives C/C++-class native execution, deterministic destruction, no GC, no JIT warm-up, and memory safety in safe Rust. This is attractive for newly isolated pricing kernels, feed-normalization services, distribution gateways, and bounded native components where you want low jitter without adopting C++ memory-risk exposure.

Where Rust is compelling

  • New component with clear boundaries and a tight latency budget.
  • Memory safety is a priority, but GC/JVM behaviour is undesirable.
  • Data ownership maps naturally to per-core/per-instrument shards.
  • Code can stay mostly safe Rust, with small reviewed unsafe/FFI sections.

Where Rust is a poor fit

  • Full rewrite of a mature Java domain platform with no measured bottleneck.
  • Heavy dependency on Java-first Aeron/Agrona or Java FIX integrations.
  • Team lacks Rust production experience and cannot staff a durable group.
  • Unsafe FFI, custom allocators, or async complexity would dominate the implementation.

Rust still needs low-latency engineering discipline: avoid heap allocation in the hot path, avoid locks, be careful with async runtimes, benchmark allocator behaviour, pin threads, pre-touch memory, and keep FFI boundaries explicit. Rust removes some JVM tail-risk classes; it does not remove OS, cache, NIC, branch, serialization, or architectural tail risks.

C++

C++ remains the reference language for many hardware-adjacent and venue-adjacent low-latency components. It follows a “zero-overhead” design principle: you should not pay for features you do not use, and what you do use should be as efficient as hand-written alternatives.[S13] That fits feed handlers, exchange gateways, DPDK, kernel bypass, custom allocators, and tightly controlled hot loops.

Where C++ is compelling

  • Sub-50µs p99.99 component budgets.
  • Vendor libraries, NIC APIs, DPDK, or exchange adapters are C/C++ first.
  • Existing firm capability in modern low-latency C++ is strong.
  • Extreme control over memory layout, ABI, compilation, and instruction path is needed.

Where C++ is risky

  • Team cannot sustain rigorous review, testing, sanitizers, and coding standards.
  • Business logic complexity is high and correctness dominates raw speed.
  • Key-person dependency is likely.
  • AI-generated or rushed code may hide undefined behaviour, races, and rare tail defects.

Java ecosystem advantage for this exact problem

Aeron’s repository states it provides efficient reliable UDP unicast, UDP multicast, and IPC message transport, with Java, C, and C++ clients available, plus same-machine IPC and persistent recording through Archive.[S3] Agrona provides high-performance Java data structures, direct/atomic buffers, primitive collections, lock-less queues, off-heap ring/broadcast buffers, and support for SBE codecs.[S4] For an Aeron/Agrona/SBE-based FX pricing system, that is a material reason not to abandon Java without a measured cause.

Rust ecosystem position

Rust has excellent general systems tooling and growing professional adoption; the Rust project’s 2024 survey reported rising use of Rust at work and non-trivial organisational use among respondents.[S14] But Rust’s finance-specific low-latency ecosystem is not yet as broad as Java’s for Aeron/Agrona/SBE/Chronicle, nor as deep as C++ for hardware-adjacent HFT components.

C++ ecosystem position

C++ has the deepest ecosystem around vendor NICs, kernel-bypass stacks, exchange connectivity, and mature commercial FIX engines. Its cost is toolchain complexity, stricter review requirements, memory-risk management, and a narrower set of engineers who can safely write p99.99-grade C++.

8. Hardware tuning caveat: below ~100µs, the hardware becomes part of the application

Once the target approaches 100µs p99.99, language choice becomes only one input. The “application” includes BIOS settings, CPU isolation, kernel configuration, NIC queues, interrupt affinity, NUMA topology, memory pre-touching, page size, power management, clock source, and deployment topology.

CPU and scheduler

  • Pin critical threads to dedicated cores.
  • Separate housekeeping cores from trading cores.
  • Disable or restrict scheduler load balancing on isolated cores.
  • Use real-time priority only with careful failure controls.

Power and memory

  • Performance governor; avoid deep C-states and frequency transitions.
  • Pre-touch memory; avoid page faults after startup.
  • Use huge pages where validated; avoid transparent huge page surprises.
  • NUMA-local allocation and NIC/core placement.

Network

  • NIC queue/IRQ affinity.
  • Busy polling where justified.
  • Kernel-bypass options such as DPDK, Onload, or equivalent.
  • Explicit backpressure/drop/replay policy for UDP bursts.

DPDK describes poll-mode drivers that bypass the kernel network stack to reduce latency and increase throughput, along with hugepage support, memory pools, ring buffers, and packet APIs.[S11] Red Hat’s low-latency TuneD profiles similarly focus on disabling power-saving mechanisms, performance CPU governor settings, low C-states, CPU partitioning, and network-latency tuning.[S17]

What this means operationally: sub-100µs systems consume dedicated cores, increase power draw, reduce infrastructure flexibility, complicate failover, require privileged OS/NIC tuning, and need engineers who can debug perf, PMU counters, kernel behaviour, NIC firmware, and latency histograms. This cost can exceed the cost of changing languages.

Key-person dependency warning: moving from mainstream Java to a niche Rust/C++/kernel-bypass/FPGA-heavy platform can create “software FPGA” risk: a small number of specialists become the release bottleneck, incident-response bottleneck, and design authority. The business cost is not only compensation; it is bus factor, recruitment lead time, onboarding time, auditability, and delayed strategy changes.

Relating niche software talent to FPGA developers

FPGA is the extreme case of this risk. A recruitment-sector article notes that FPGA development is much more difficult than software, deployment lead times can be lengthy, ongoing support is in short supply, and candidates with the right financial plus engineering combination can command high salaries.[S18] A current London HFT FPGA role advertised by Oxford Knight lists £200k base plus bonus.[S19] Rust is not as niche as FPGA, but a full Rust rewrite of an FX market-making platform can move the organisation in that direction if only one or two people truly understand the low-latency Rust hot path.

Mitigation if adopting Rust or C++

  • Keep the native hot path small, stable, and bounded; do not rewrite control-plane or non-critical services.
  • Require at least three maintainers per critical component, not one expert.
  • Mandate deterministic replay, property tests, fuzzing where useful, latency regression CI, code-generation for schemas, and runbooks.
  • Prefer language-neutral wire contracts: SBE schemas, well-defined event logs, reproducible inputs and outputs.
  • Budget hiring and training before committing to the rewrite, not after.

10. AI-agent coding: Rust vs Java vs C++

There is no strong evidence that AI agents are categorically better at writing production-grade low-latency Rust than Java. The evidence supports a more nuanced view: AI tools can improve productivity on bounded coding tasks, but their output needs human verification, especially for complex systems.

ClaimEvidenceImplication
AI can improve coding productivity.A controlled GitHub Copilot experiment found developers completed a JavaScript HTTP-server task 55.8% faster with Copilot.[S20]Use AI for scaffolding, tests, documentation, migration scripts, wrappers, and benchmark harnesses.

Practical view by language

Java + AI

Likely easiest for agents in ordinary enterprise code, APIs, tests, refactors, and tooling because examples and libraries are abundant. Low-latency Java remains specialized; agents may accidentally allocate, add logging, use blocking queues, or introduce framework overhead.

Rust + AI

The Rust compiler gives agents strong feedback loops, and safe Rust reduces memory-risk classes. But ownership, lifetimes, async, unsafe, FFI, and no-allocation design can reduce first-pass success. AI can help but will not eliminate Rust learning cost.

C++ + AI

Agents can generate plausible C++ quickly, but compile success is not enough. Undefined behaviour, lifetime bugs, races, false sharing, allocator surprises, and rare-tail defects are hard for agents to detect without strong tests and expert review.

AI recommendation: use agents to accelerate non-hot-path migration work, test generation, benchmark harnesses, docs, schema codegen, and repetitive adapters. For pricing/distribution hot paths, require human review plus latency regression evidence before merge.

11. Recommended decision path

1. Freeze the target into a measurable SLA

  • Define p50/p99/p99.9/p99.99 for each stage and full path.
  • Define message sizes, rates, bursts, client counts, currency pairs, model complexity, persistence/encryption settings, and failure modes.
  • Separate quote-distribution latency from client deal-acceptance latency.

2. Build a production-like benchmark harness before language migration

  • Use market replay and stress bursts, not synthetic average load only.
  • Measure coordinated-omission-safe histograms; report p99.99 and maximums.
  • Run single-host IPC, network, failover, and degraded-mode tests.
  • Compare Java optimized baseline against Rust and C++ prototypes using identical wire formats and hardware.

3. Optimize current Java first

  • Remove allocation after startup in pricing/distribution paths.
  • Use SBE/Agrona/direct buffers and primitive collections where appropriate.
  • Replace blocking queues and shared locks with single-writer ring/event-loop patterns.
  • Pre-touch memory; set heap strategy; collect safepoint/JFR/perf data.
  • Pin threads; isolate cores; validate NUMA and NIC affinity.

4. Prototype only the measured bottleneck in Rust and/or C++

Candidate prototypes:

  • Pricing kernel for a subset of currency pairs.
  • Market-data normalization or distribution gateway.
  • SBE/Aeron bridge with native fan-out.
  • Deal-acceptance micro-kernel excluding FIX session management.

5. Choose using a scorecard, not a slogan

Final recommendation

Adopt a hybrid strategy: keep Java as the platform default, invest in low-latency Java and hardware tuning, and create a narrowly scoped Rust/C++ benchmark lane for specific hot-path components. Revisit a broader Rust strategy only if the pilot proves material p99.99 improvement after accounting for hiring, ecosystem, operational, and migration risk.
